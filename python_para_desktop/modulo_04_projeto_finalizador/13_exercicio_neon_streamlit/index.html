    13 — Exercício Prático: Banco em Nuvem com Neon + Streamlit¶

    🎯 Objetivo¶

    Neste capítulo-exercício você vai construir um app web de gerenciamento de tarefas usando Python, Streamlit e um banco de dados PostgreSQL em nuvem (Neon Database).

    Ao final, você terá:

    • Um projeto no Neon Database com banco PostgreSQL funcionando na nuvem
    • Tabelas usuarios e tarefas criadas com SQL real (PostgreSQL)
    • Um sistema de cadastro e login de usuários com senha protegida por hash e sal
    • Um CRUD completo de tarefas com status (Em Aberto, Realizando, Em Atraso)
    • Controle de datas (criação e prazo limite) com detecção automática de atraso
    • O arquivo .env protegendo as credenciais do banco
    • A experiência de usar Python na web com Streamlit

    Por que este exercício?

    Nos capítulos anteriores você construiu o Sistema Escolar como uma aplicação desktop com Tkinter e SQLite. Agora, vamos mudar o cenário: em vez de desktop, vamos para a web. Em vez de SQLite local, vamos usar um banco de dados PostgreSQL em nuvem. Isso mostra a versatilidade do Python — a mesma linguagem que você já domina serve para desktop, web, automação, ciência de dados e muito mais.

    📍 Contextualização¶

    Você já domina Python, já construiu interfaces gráficas com Tkinter, já conectou ao SQLite, já fez CRUD completo e, no Capítulo 09, levou o Sistema Escolar para o banco em nuvem do Neon. Agora, vamos expandir seu repertório com duas ferramentas poderosas do ecossistema Python:

    Streamlit — uma biblioteca que transforma scripts Python em aplicações web interativas. Sem precisar de HTML, CSS ou JavaScript. Você escreve Python puro e o Streamlit gera a interface web automaticamente.

    Neon Database — o mesmo banco PostgreSQL em nuvem do Capítulo 09, com plano gratuito generoso. A diferença é quem conversa com ele: em vez de uma janela Tkinter, uma página web. O SQL, o .env e o driver psycopg são os mesmos que você já usou.

    💻 Implementação Guiada¶

    Passo 1 — Criando o projeto no Neon Database¶

    Este exercício usa um banco separado do Sistema Escolar. Siga o mesmo caminho do Capítulo 09:

    • 18 anos ou mais: na sua conta do Neon, clique em New project ➔ Project name: exercicio-tarefas ➔ Region: AWS South America East 1 (São Paulo) ➔ Create project. Depois, Connect ➔ Copy snippet.
    • Menos de 18 anos: o Neon não é direcionado a menores de 18. Peça ao professor a connection string do banco do exercício.

    A connection string se parece com isto:

    postgresql://usuario:SENHA@ep-nome-123456.sa-east-1.aws.neon.tech/neondb?sslmode=require&channel_binding=require

    Erro Crítico

    Copie essa connection string e guarde em um lugar seguro. Ela contém sua senha! Nunca cole no código-fonte diretamente — vamos usar o .env para protegê-la.

    Conceito Importante

    O PostgreSQL é o banco de dados relacional mais avançado do mundo open-source. Diferente do SQLite (que é um arquivo local), o PostgreSQL roda em um servidor e aceita conexões remotas. O plano gratuito do Neon oferece 1 GB de armazenamento por projeto — mais do que suficiente para nosso exercício.

    Passo 3 — Módulo de conexão com o banco (database.py)¶

    Crie o arquivo database.py. Ele será responsável por toda a comunicação com o Neon Database.

    Comece com a conexão e a criação das tabelas:

    # ======================================================================
# database.py — Conexão e operações com Neon Database
# ======================================================================
# Eu sou responsável por toda a comunicação com o banco PostgreSQL
# na nuvem. Uso o psycopg (versão 3) para conectar e executar SQL.
# ======================================================================

import os
import hashlib
import hmac
import secrets
from datetime import date, datetime
from dotenv import load_dotenv
import psycopg
from psycopg.rows import dict_row

# Eu carrego as variáveis de ambiente do arquivo .env.
load_dotenv()


def conectar():
    """
    Eu abro uma conexão com o banco Neon Database.
    Retorno a conexão pronta para uso.
    """
    database_url = os.getenv("DATABASE_URL")
    if not database_url:
        raise ValueError(
            "DATABASE_URL não encontrada. "
            "Verifique o arquivo .env"
        )
    # Eu conecto usando a URL completa do Neon.
    # row_factory=dict_row faz cada linha vir como dicionário.
    conn = psycopg.connect(database_url, row_factory=dict_row)
    return conn

    Conceito Importante

    O psycopg é o driver mais usado para conectar Python ao PostgreSQL (a versão 3, que usamos aqui e no Capítulo 09, é a recomendada pelo Neon; você ainda vai ver a versão antiga, psycopg2, em muitos tutoriais). A connection string (DATABASE_URL) contém tudo: usuário, senha, host, porta e nome do banco. O sslmode=require garante que a conexão é criptografada — essencial para bancos em nuvem.

    Agora, adicione a função que cria as tabelas:

    def criar_tabelas():
    """
    Eu crio as tabelas no banco se elas ainda não existirem.
    Uso IF NOT EXISTS para evitar erros na segunda execução.
    """
    conn = conectar()
    cursor = conn.cursor()

    # Eu crio a tabela de usuários.
    cursor.execute("""
        CREATE TABLE IF NOT EXISTS usuarios (
            id SERIAL PRIMARY KEY,
            nome VARCHAR(100) NOT NULL,
            email VARCHAR(150) UNIQUE NOT NULL,
            senha_hash VARCHAR(128) NOT NULL,
            sal VARCHAR(32) NOT NULL,
            data_cadastro TIMESTAMP DEFAULT NOW()
        )
    """)

    # Eu crio a tabela de tarefas.
    # Cada tarefa pertence a um usuário (usuario_id).
    cursor.execute("""
        CREATE TABLE IF NOT EXISTS tarefas (
            id SERIAL PRIMARY KEY,
            titulo VARCHAR(200) NOT NULL,
            descricao TEXT,
            status VARCHAR(20) DEFAULT 'Em Aberto',
            data_criacao TIMESTAMP DEFAULT NOW(),
            data_limite DATE,
            usuario_id INTEGER REFERENCES usuarios(id)
        )
    """)

    conn.commit()
    cursor.close()
    conn.close()

    Dica Profissional

    No PostgreSQL, SERIAL gera IDs automáticos (equivalente ao INTEGER PRIMARY KEY AUTOINCREMENT do SQLite). O REFERENCES usuarios(id) cria uma chave estrangeira — o banco garante que toda tarefa pertence a um usuário válido. Se tentar inserir uma tarefa com um usuario_id inexistente, o banco rejeita.

    Passo 4 — Funções de usuário (cadastro e login)¶

    Continue no database.py. Adicione as funções de cadastro e autenticação:

    def gerar_hash(senha, sal):
    """
    Eu transformo a senha em um hash com o scrypt, misturando o sal.
    O scrypt é lento de propósito: atrapalha quem tenta adivinhar
    milhões de senhas por segundo.
    """
    hash_bytes = hashlib.scrypt(
        senha.encode(), salt=sal, n=2**14, r=8, p=1, dklen=64
    )
    return hash_bytes.hex()


def cadastrar_usuario(nome, email, senha):
    """
    Eu cadastro um novo usuário no banco.
    Guardo o hash da senha e o sal, nunca a senha em texto puro.
    Retorno True se sucesso, False se o email já existe.
    """
    conn = conectar()
    cursor = conn.cursor()
    try:
        # Eu sorteio um sal novo (16 bytes aleatórios) para cada usuário.
        sal = secrets.token_bytes(16)
        senha_hash = gerar_hash(senha, sal)
        cursor.execute("""
            INSERT INTO usuarios (nome, email, senha_hash, sal)
            VALUES (%s, %s, %s, %s)
        """, (nome, email, senha_hash, sal.hex()))
        conn.commit()
        return True
    except psycopg.errors.UniqueViolation:
        # O email já está cadastrado no banco.
        conn.rollback()
        return False
    finally:
        cursor.close()
        conn.close()

    Conceito Importante

    O hash é uma via de mão única: não existe uma conta que transforme "a1b2c3d4e5f6..." de volta em "minha_senha_123". Mas quem rouba o banco pode adivinhar: calcula o hash de "123456", "senha123" e de milhões de senhas comuns e compara com o que está na tabela. Com um hash rápido e sem sal (como o SHA-256 puro), isso leva segundos — e duas pessoas com a mesma senha teriam o mesmo hash.

    Por isso usamos duas defesas, ambas da biblioteca padrão do Python (não precisa instalar nada):

    • Sal: 16 bytes sorteados com secrets para cada usuário e misturados à senha antes do hash. A mesma senha vira hashes diferentes, e listas prontas de hashes não servem mais. O sal não é segredo: fica guardado na coluna sal, ao lado do hash.
    • scrypt: um hash feito para ser lento e gastar memória. Para você, que faz login uma vez, a diferença é imperceptível; para quem testa milhões de palpites, cada um fica caro.

    Nenhuma das duas salva uma senha fraca como "123456" — ela continua entre os primeiros palpites. Por isso o app exige um tamanho mínimo de senha.

    Agora, a função de login:

    def autenticar_usuario(email, senha):
    """
    Eu verifico se o email e a senha correspondem
    a um usuário cadastrado no banco.
    Retorno os dados do usuário se autenticado, None se não.
    """
    conn = conectar()
    cursor = conn.cursor()

    # Eu busco o usuário só pelo e-mail: preciso do sal dele
    # para refazer a conta com a senha digitada.
    cursor.execute("""
        SELECT id, nome, email, senha_hash, sal FROM usuarios
        WHERE email = %s
    """, (email,))

    usuario = cursor.fetchone()
    cursor.close()
    conn.close()

    if usuario is None:
        return None

    # Eu calculo o hash da senha digitada com o MESMO sal do cadastro.
    tentativa = gerar_hash(senha, bytes.fromhex(usuario["sal"]))

    # Eu comparo com hmac.compare_digest, que leva o mesmo tempo
    # acertando ou errando: não dá pistas a quem mede o tempo da resposta.
    if not hmac.compare_digest(tentativa, usuario["senha_hash"]):
        return None

    # Eu devolvo só o que o app precisa: nunca o hash nem o sal.
    return {
        "id": usuario["id"],
        "nome": usuario["nome"],
        "email": usuario["email"],
    }

    Perceba que no PostgreSQL usamos %s como placeholder (no SQLite, usamos ?). O funcionamento é o mesmo: protege contra SQL Injection.

    Dica Profissional

    Repare que o login não procura “e-mail e senha” no WHERE, como faria com uma senha guardada em texto puro. Como cada usuário tem o seu sal, o banco não consegue comparar sozinho: primeiro buscamos o usuário pelo e-mail e depois o Python refaz o hash e compara. Note também que e-mail inexistente e senha errada devolvem o mesmo None — o app mostra a mesma mensagem nos dois casos e não revela quais e-mails estão cadastrados.

    Passo 5 — Funções de tarefas (CRUD)¶

    Continue no database.py. Adicione as operações CRUD para tarefas:

    def criar_tarefa(titulo, descricao, data_limite, usuario_id):
    """
    Eu insiro uma nova tarefa no banco.
    O status inicial é sempre 'Em Aberto'.
    """
    conn = conectar()
    cursor = conn.cursor()
    cursor.execute("""
        INSERT INTO tarefas
            (titulo, descricao, data_limite, usuario_id)
        VALUES (%s, %s, %s, %s)
    """, (titulo, descricao, data_limite, usuario_id))
    conn.commit()
    cursor.close()
    conn.close()


def listar_tarefas(usuario_id):
    """
    Eu busco todas as tarefas de um usuário específico.
    Retorno como lista de dicionários, ordenadas por data.
    """
    conn = conectar()
    cursor = conn.cursor()
    cursor.execute("""
        SELECT * FROM tarefas
        WHERE usuario_id = %s
        ORDER BY data_criacao DESC
    """, (usuario_id,))
    tarefas = cursor.fetchall()
    cursor.close()
    conn.close()
    return tarefas

    Agora, as funções de atualizar e excluir:

    def atualizar_status(tarefa_id, novo_status):
    """
    Eu altero o status de uma tarefa.
    Os status possíveis: 'Em Aberto', 'Realizando', 'Concluída'.
    """
    conn = conectar()
    cursor = conn.cursor()
    cursor.execute("""
        UPDATE tarefas SET status = %s WHERE id = %s
    """, (novo_status, tarefa_id))
    conn.commit()
    cursor.close()
    conn.close()


def excluir_tarefa(tarefa_id):
    """
    Eu removo uma tarefa do banco permanentemente.
    """
    conn = conectar()
    cursor = conn.cursor()
    cursor.execute(
        "DELETE FROM tarefas WHERE id = %s",
        (tarefa_id,)
    )
    conn.commit()
    cursor.close()
    conn.close()

    ⚠️ Erros Comuns¶

    Connection string inválida ou ausente

    Sintoma: ValueError: DATABASE_URL não encontrada ou psycopg.OperationalError: connection failed.

    Causa: O arquivo .env não existe, está vazio, ou a connection string está incorreta. Outra causa comum: copiar a URL com espaços extras.

    Solução: Verifique se o arquivo .env está na mesma pasta do app.py. Abra o .env e confirme que a DATABASE_URL está preenchida corretamente. Copie a URL novamente do painel do Neon. Não use aspas ao redor da URL no .env.

    Erro de SSL ao conectar ao Neon

    Sintoma: psycopg.OperationalError: SSL SYSCALL error.

    Causa: A connection string não inclui ?sslmode=require ou a rede está bloqueando conexões SSL (comum em redes corporativas/escolares).

    Solução: Confirme que a URL tem sslmode=require (copie de novo com Copy snippet). Se estiver em uma rede restritiva, tente usar uma rede diferente (hotspot do celular, por exemplo). O Neon exige SSL obrigatoriamente.

    E-mail duplicado no cadastro

    Sintoma: psycopg.errors.UniqueViolation: duplicate key value violates unique constraint.

    Causa: Tentou cadastrar com um e-mail que já existe. Nossa função já trata isso, mas se você não usou o try/except, o erro aparece.

    Solução: Verifique se a função cadastrar_usuario tem o bloco except psycopg.errors.UniqueViolation que retorna False. No app, exiba uma mensagem amigável ao usuário.

    Coluna senha_hash ou sal não existe

    Sintoma: psycopg.errors.UndefinedColumn: column "senha_hash" of relation "usuarios" does not exist ao cadastrar.

    Causa: A tabela usuarios foi criada antes, com outras colunas (por exemplo, numa versão antiga deste exercício com a coluna senha). O CREATE TABLE IF NOT EXISTS não mexe em tabela que já existe.

    Solução: Se os dados forem só de teste, apague as tabelas no SQL Editor do Neon — primeiro DROP TABLE tarefas;, depois DROP TABLE usuarios; (nessa ordem, por causa da chave estrangeira) — e rode o app de novo para recriá-las. Os usuários antigos precisam se cadastrar outra vez: não há como converter um hash antigo, porque a senha original não está guardada em lugar nenhum.

    Cadastro funciona, mas o login sempre falha

    Sintoma: O usuário acabou de se cadastrar e, no login, sempre aparece "E-mail ou senha incorretos!".

    Causa: O autenticar_usuario sorteou um sal novo em vez de usar o sal guardado no cadastro (com outro sal, o hash sai diferente), ou os parâmetros do scrypt mudaram entre o cadastro e o login.

    Solução: No login, use bytes.fromhex(usuario["sal"]) — o sal que veio do banco. O sal sorteado com secrets.token_bytes(16) só aparece no cadastrar_usuario. Mantenha os mesmos n, r, p e dklen nos dois lugares (por isso os dois chamam a mesma função gerar_hash).

    Session state perdido ao atualizar a página

    Sintoma: O usuário faz login, mas ao pressionar F5 (atualizar a página) é deslogado.

    Causa: O session_state do Streamlit só persiste durante a sessão ativa no navegador. Atualizar a página reinicia a sessão.

    Solução: Este é o comportamento esperado do Streamlit. Para uma solução mais robusta, seria necessário usar cookies ou tokens JWT — mas isso está além do escopo deste exercício. Informe os alunos que é normal.

    Tarefas não aparecem após criar

    Sintoma: O formulário confirma "Tarefa criada!", mas a tarefa não aparece na lista.

    Causa: O st.rerun() não foi chamado após a inserção, ou a função listar_tarefas está filtrando por outro usuario_id.

    Solução: Confirme que há um st.rerun() logo após o st.success() no botão de criar. Verifique se o usuario_id passado para criar_tarefa e listar_tarefas é o mesmo (vindo de st.session_state["usuario"]["id"]).

    💡 Boas Práticas¶

    1. Separação de responsabilidades

    O database.py cuida do banco, o app.py cuida da interface. Nenhum código SQL aparece no app.py, nenhum widget Streamlit aparece no database.py. Essa separação é o mesmo princípio que você aplicou no Sistema Escolar com a arquitetura MVC. No mundo real, projetos grandes têm dezenas de módulos separados.

    2. Credenciais protegidas com .env

    A DATABASE_URL contém sua senha. Se alguém acessar essa string, terá controle total sobre seu banco. Usar .env e .gitignore é o padrão da indústria. Serviços como Heroku, Vercel e o próprio Streamlit Cloud usam variáveis de ambiente para configuração — você já está aprendendo o jeito profissional.

    3. Hash de senhas obrigatório

    Nunca armazene senhas em texto puro — nem com um hash rápido e sem sal, como o SHA-256 puro, que se adivinha em segundos para senhas comuns. Use um hash lento com sal aleatório por usuário, como o scrypt deste exercício (já vem no Python). No mercado, o Django já faz isso por você; em outros projetos, bibliotecas como argon2-cffi e bcrypt são as escolhas mais comuns. E nunca invente o seu próprio esquema de criptografia: use os que já foram testados.

    4. SQL parametrizado contra SQL Injection

    Usamos %s como placeholder em vez de concatenar strings no SQL. Isso protege contra SQL Injection — um ataque onde o usuário digita código SQL malicioso no campo de entrada. Se alguém digitar '; DROP TABLE tarefas; -- no campo de título, o %s trata como texto puro, não como comando SQL.

    5. Banco em nuvem vs banco local

    O SQLite é perfeito para aplicações desktop single-user. O PostgreSQL em nuvem (Neon) é ideal para apps web multi-user. Saber quando usar cada um é uma habilidade essencial para desenvolvedores. A regra geral: se mais de uma pessoa vai acessar os dados ao mesmo tempo → use um banco em nuvem.
